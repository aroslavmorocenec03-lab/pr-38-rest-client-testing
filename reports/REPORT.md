# Звіт до практичної роботи №38

**Тема:** перевірка роботи API-ендпойнтів за допомогою REST Client.

## Виконана робота

У VS Code встановлено розширення `humao.rest-client` версії **0.25.1** з Marketplace. Підготовлено один `requests.http`, де запити об’єднані в повний CRUD-цикл для одного нового відправлення. Кожен блок має маркер `###`, номер, опис та ім’я запиту. POST і PUT містять `Content-Type: application/json` і JSON-тіло.

Id нового запису передається між запитами через `{{createPosting.response.body.$.id}}`. Це дозволяє повторювати сценарій без ручної зміни адрес після кожного POST.

Для відтворення включено навчальний сервер із ПР-37. Додано підтримку рядкових значень `DeliveryType`, які використані в прикладах цієї роботи. Адреса — `http://localhost:5050`, відповідно до фактичного налаштування проєкту.

## Підтверджені HTTP-результати

Файл `requests.http` фактично виконано додатковим сценарієм PowerShell 7, який читає URL, методи, JSON і змінні з цього файлу. Усі **10/10** запитів пройшли перевірки. Це протокол автоматичної HTTP-перевірки; його не подано як знімок інтерфейсу REST Client.

| Запит | Отримано | Що підтверджено |
| --- | --- | --- |
| GET списку перед змінами | 200 | Початковий список і `application/json` |
| GET наявного Id=1 | 200 | Повернувся саме потрібний запис |
| GET відсутнього Id=999999 | 404 | Відсутній ресурс не повертається як успішний |
| POST | 201 | Створено відправлення Ivan → Olena; є `Location` та серверний Id |
| Повторний GET списку | 200 | Кількість збільшилася на один; новий Id присутній |
| GET створеного запису | 200 | Початковий вміст — `Documents` |
| PUT | 200 | Вміст — `Documents (updated)`, доставка — `Courier`, вага — 0.6, цінність — 120, ціна — 20; Id та час створення збережені |
| GET після PUT | 200 | Тіло відповіді збігається з оновленим записом, отже зміни збережені в пам’яті |
| DELETE | 204 | Запит успішний, тіло порожнє |
| GET після DELETE | 404 | Той самий запис уже відсутній |

Повний протокол із реальними заголовками та JSON: [http-results.txt](http-results.txt).

### Межа перевірки інтерфейсу

Встановлення розширення підтверджене через CLI VS Code, див. [rest-client-extension.txt](rest-client-extension.txt). Натискання Send Request у графічному інтерфейсі поки не перевірено: вікно `requests.http — Visual Studio Code` згорнуте, а засіб керування повідомив, що не може отримати його стан. Користувачеві надіслано прохання розгорнути вікно. Наведені вище результати стосуються реальних HTTP-запитів із доданого файлу, виконаних сценарієм PowerShell.

## Аналіз статусів

- **200 OK** — читання або редагування успішне; тіло потрібно також перевірити на правильність даних.
- **201 Created** — новий ресурс створено; `Location` указує на його адресу.
- **204 No Content** — операція виконана, тіло відсутнє; видалення підтверджується наступним GET.
- **404 Not Found** — ресурс відсутній. У запитах 03 і 10 це очікуваний успішний результат негативного тесту.

Самого правильного статусу недостатньо: у роботі також перевірено появу нового запису в списку, збереження змін і фактичне видалення.

## Висновок

Один файл запитів охопив повний цикл CRUD. Послідовність GET → POST → GET → PUT → GET → DELETE → GET дозволила перевірити не лише відповіді, а й зміни серверного стану. Іменований POST зробив наступні звернення незалежними від наперед заданого Id.

## Відповіді на контрольні запитання

1. **Що таке REST Client?** У цій роботі це розширення VS Code від Huachao Mao (`humao.rest-client`), яке надсилає HTTP-запити з редактора та показує відповіді.
2. **Як перевірити API без браузера?** Через REST Client, `curl`, PowerShell, окремий HTTP-клієнт або автоматизовану програму. Так можна задати метод, заголовки й тіло запиту.
3. **Для чого файли .rest?** Вони зберігають текстові HTTP-запити та параметри повторюваних сценаріїв. REST Client також підтримує розширення `.http`, використане тут.
4. **Як формується HTTP-запит?** Спочатку метод і адреса, потім заголовки, порожній рядок і, за потреби, тіло. Для JSON у POST і PUT задається відповідний `Content-Type`.
5. **Як розуміти статус?** Код показує результат обробки: 2xx — успішна відповідь, 4xx — проблема запиту або доступності ресурсу, 5xx — серверний збій. Конкретне значення порівнюють з очікуванням тесту; 404 є правильним для відсутнього запису.
6. **Що означає коректна відповідь API?** Правильний статус, потрібні заголовки та правильне тіло згідно з контрактом, а для зміни даних — також відповідний новий стан сервера.
7. **Як перевірити JSON?** Переглянути `Content-Type: application/json`, переконатися, що тіло коректно розбирається як JSON, і перевірити очікувані поля, типи та значення.
8. **Чому важливо перевіряти маршрут?** Помилка шляху, порту, Id або HTTP-методу може спрямувати запит не до потрібного обробника. Це здатне спричинити 404 чи 405 навіть за справного сервера.
9. **Як виявляти помилки при тестуванні?** Порівнювати очікувані й фактичні статуси, заголовки та дані, виконувати повторні GET після змін, перевіряти відсутні Id, аналізувати повідомлення та журнал сервера.
10. **Які результати показує успішний тест?** Запит до правильного маршруту завершується очікуваним статусом; JSON і заголовки відповідають контракту; створення, оновлення або видалення підтверджено незалежним наступним запитом. Для негативного тесту очікувана помилка також є успіхом.
